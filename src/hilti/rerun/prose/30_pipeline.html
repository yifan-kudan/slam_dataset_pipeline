03  the pipeline

Seven steps, run in one order for all fifteen

Each stage below produces exactly one artefact and the next stage reads it, which is why the order is not negotiable: the map has to be levelled before it is converted, because the levelling is applied by the converter; and the levelling itself comes out of the FAST-LIO run that produced the cloud, so pairing a map with another run's gravity state silently rotates everything downstream.

01

The bag

Hilti ships ROS 1 recordings. src/rosbag1_to_ros2.py re-containers each one into a ROS 2 bag carrying only /velodyne_points and /imu, with the Hesai and Bpearl clouds repacked to the Velodyne field layout so one handler reads both. Unchanged in this run — the same fifteen bags as before.

02

FAST-LIO, at full frame rate

src/batch_fastlio.py --run-name rerun_r1.0 -r 1.0, one bag at a time because FAST-LIO is a single global ROS graph driven by /clock. Two things every run gets whether it asks or not: the Fast DDS profile that stops the writer discarding clouds, and frame accounting that fails a run below 95 % of the bag's own cloud count. That second one is the point of this campaign — see the next section.

03

Score the trajectory

src/hilti/eval_fastlio.py: control-point pair distances against the survey, plus three divergence detectors (max |v|, peak accelerometer bias, worst displacement over any 9 s window) and the frame percentage. The detectors exist because a sequence can pass its control points and still have blown up after the last one.

04

Measure the map frame's gravity

src/hilti/align_map.py reads the mid-run median of FAST-LIO's own S2 gravity state and computes the rotation that levels it. This is not cosmetic: kd_localizer seeds its ESKF gravity at the map frame's −Z and never revisits the choice, while a FAST-LIO map frame is the IMU frame at the first processed scan — so it inherits however the IMU was bolted on. The handheld rig lands ~178–180° from that assumption and the robot ~90°.

05

Cloud → levelled LAS

pdal translate with a transformation filter carrying the matrix from step 4, quantised to 1 mm rather than PDAL's 1 cm default — LAS stores integers, and a centimetre is coarse next to a 0.25 m plane voxel fitted to 0.01 m.

06

LAS → .kdm

The release ships build_map as a Polyscope GUI with no working CLI, so a small headless driver calls the same shipped entry points — PlaneMap::construct, Bbs3dMap::construct, LocalizerMap::save. Library defaults throughout: 0.25 m plane voxels, 0.01 m plane-fit sigma, a 3D-BBS pyramid at twice the voxel size over seven levels.

07

Replay the bag against the map

kd_localizer_node inside the Humble release container, -r 1, track_only true, relocalizer off, use_sim_time true. Ten of the fifteen bags were re-containered without /tf_static, so imu_link → velodyne is republished at run time; without it the node sits at UNINITIALIZED forever, because it has to look the extrinsic up in TF while FAST-LIO reads its own from config.

Why -r 1 and not slower

Both stages play at real time and neither wants anything else. kd_localizer has a 20 Hz process_frequency, so playing faster discards frames outright, and playing slower buys nothing because it is not on a best-effort subscription. FAST-LIO is best-effort, but its loss was writer-side, which is rate-independent — the earlier r0.15 and r0.3 runs lost 49.2 % and 50.2 % of their clouds respectively, and that near-equality is what proves rate was never the knob.
