02  why re-run anything

Every earlier number was computed from half the data

The Hilti 2023 evaluation had been run before, sequence by sequence, and it reported figures that looked reasonable. Then the reason one sequence "could not be mapped" turned out to be that FAST-LIO had only ever seen 47 % of its LiDAR frames — and that this was true of every run in the workspace, at 45–53 %.

The cause is not FAST-LIO and not the network. Its cloud subscription is rclcpp::SensorDataQoS() — best-effort, KeepLast(5) — while a Hilti cloud is 1.37 MB. Fast DDS carries intra-host payload over shared memory, so the kernel's UDP counters stay at zero throughout, and the default shared-memory segment cannot hold that sample stream: when the writer finds no free buffer, best-effort drops at the writer rather than waiting. Raising net.core.rmem_max does nothing. Deepening the reader's queue does nothing — 67 % loss became 65 %, which places the drop upstream of the reader entirely.

What does work is a larger segment, declared outside the code so that upstream QoS stays exactly as a real LiDAR driver would need it: 

config/dds/fastdds_shm_big.xml, exported as FASTRTPS_DEFAULT_PROFILES_FILE
for the node AND for `ros2 bag play` -- they share one environment

<segment_size>134217728</segment_size>           128 MB, up from 512 KB
<maxMessageSize>4194304</maxMessageSize>
<port_queue_capacity>1024</port_queue_capacity>

maxMessageSize is camelCase. The snake_case spelling fails XML
validation and silently voids the whole profile -- Fast DDS logs
nothing, and every cloud is lost exactly as before.

With it, a synthetic 10 Hz stream of 1.37 MB samples arrives complete (200 of 200, against 67 without), and a real bag delivers 929 of 929 clouds against 331. That fix landed as a default in src/batch_fastlio.py, which is why this campaign exists: no result in the previous report is comparable to one taken after it, so the whole dataset had to go through the pipeline again from the bag.

The re-run is also the first chance to ask a question the dataset was built for and the earlier evaluation never touched. Giving every sequence its own map is the easy case twice over: the map contains exactly the geometry the bag is about to see, and the map frame is the rig's start pose, so tracking begins from a known identity with no prior to supply. Building once and localizing on every later visit is the case that matters on a site — so this run also picks one hub map per site and replays every other sequence of that site against it.
